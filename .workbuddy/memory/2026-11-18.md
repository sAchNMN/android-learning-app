### 坑：`adb reverse` 规则在本机活不过一次调用

```
调用 1：adb reverse tcp:8080 tcp:8080   → --list 显示 UsbFfs tcp:8080 tcp:8080
调用 2：adb reverse --list             → 空
```

每次调用 adb 都打 `daemon not running; starting now`，daemon 随 Bash 调用结束被杀

## 推荐页滑动卡顿排查（18:20-18:35，真机 gfxinfo 实测 + 已修）

用户报「滑到中段有轻微卡顿」。真机 `10AF3K2JLY004Q5`（1216×2640 @560dpi），
用 `dumpsys gfxinfo` 量化，修复前后对比如下（同一套 12 次 swipe 脚本）：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| Janky frames | 4.2% / 5.3% / 5.7% / **16.3%** | **0.43% / 0.44% / 0.43%** |
| 50th | 13~15ms | 10~11ms |
| 95th | 17~21ms | 13~14ms |
| Slow bitmap uploads | 4 / 10 / 20 / **55** | **0** |
| Slow issue draw commands | 8 / 19 / 27 / **65** | 1~2 |
| 冷启动立即滑 | — | 0%（p50 9ms） |

**两个真因（都不是「RecyclerView 没回收」这种教科书答案）：**

1. **`CoverArt` 的 LruCache 容量单位写错**，缓存从来没命中过。
   `LruCache<String, Bitmap>(32)` + `sizeOf` 返回 KB（168px 封面 ≈ 113KB）→
   单张图就超过 32 的上限，`put` 进去立刻被自己挤掉。
   于是**每次绑定一行都在主线程现画一张 ARGB_8888 + 4 层全画布渐变**。
   这就是 `Slow bitmap uploads` 的来源。改成 `CACHE_KB = 6 * 1024`（与 sizeOf 同为 KB）。
   顺带 `bindArt` 改成 `width > 0` 时用视图真实宽度，调用方传的 220px 全是估的
   （48dp @3.5x 实际 168px，多画 70% 面积）。

2. **收藏变化走 `notifyDataSetChanged()`**。推荐页是 NestedScrollView 套
   `wrap_content` 的 RecyclerView（不回收），全量刷新 = 20 行全部重绑
   （每行再触发一次上面那张位图）+ 整页 requestLayout 重新测量。
   触发时机恰好是进页面后 1~2 秒**静默同步 `syncLibrary` 回写收藏**、
   或者用户顺手点赞那一刻 —— 正是「滑到中段」的时间窗。
   改法：红心状态并进 item（`Row(track, liked)`），收藏变化重新 `submitList`，
   由 DiffUtil 的 `getChangePayload` 只发 `PAYLOAD_LIKE`，`onBindViewHolder` 收到 payload
   就只刷红心；`itemAnimator = null`（wrap_content 列表的 change 动画会连着整页重测）。
   点击红心时先乐观 `bindLike(新值)` 再等 diff，手感不慢半拍。

另外两个小修：
- `animateRows` 加 `userScrolled` 护栏：用户已经在滑就不再补播行入场。
  alpha<1 的 View 每帧要走离屏合成，6 个解析弹簧同时跑会和滚动抢帧。
  最常见触发场景正是「推荐结果比手指晚到」。

**排除掉的怀疑对象（重要，别再走回头路）：**
玻璃层 `GlassSurfaceView` 一开始被当成主嫌（滚动时每 50ms 把整页子树
重新 `RenderNode.record` 一遍，还挂 blur+AGSL 折射的 RenderEffect）。
实测 A/B 推翻了：没有迷你播放器时 p50 10ms、有播放时 13ms，但两者的
`Slow bitmap uploads` 差距（0 vs 20）是**上面第 1 条**造成的，不是玻璃。
所以玻璃的采样间隔**没有改**（50ms 保住了视觉上的跟手）。
以后怀疑渲染问题，先看 `Slow bitmap uploads` 是不是 0 —— 它非 0 就是有东西在造位图，
而不是绘制指令太重。

**排查手法（可复用）：**
```bash
adb shell dumpsys gfxinfo com.szc.learning reset
# ... 执行固定的 swipe 序列 ...
adb shell dumpsys gfxinfo com.szc.learning | sed -n '/Total frames rendered/,/Number Frame deadline missed (legacy)/p'
```
- `framestats` 在这台机子上不输出（只回普通统计），不要指望逐帧 CSV。
- `setprop debug.hwui.profile true` 要 force-stop 重启 App 才生效，
  能拿到 Draw/Prepare/Process/Execute 四段耗时，但**开着它本身会改变时序**
  （卡顿率从 16% 掉到 0.39%），只能看相对分布，不能当基线。
- 对比实验一定要保持「页面内容 / 滚动距离」一致。有一次拿「本地」页当对照组，
  结果那里只有 1 首歌压根不能滚，白测一轮 —— 帧数（236 vs 532）就是破绽。

### 第二轮（18:35-18:50）：用户仍报卡顿，挖到设备基线

**关键前提：这块屏是 90Hz**（`dumpsys display` → `activeMode id=4, vsyncRate=90, VSYNC period 11.1ms`），
帧预算 11.1ms 不是 16.6ms。所以 p50 10ms 已经是「每帧贴着天花板跑」，
而 `dumpsys gfxinfo` 的 Janky 计数按 16.6ms 判，会显示「只有 0.4% 卡」——**统计和体感对不上**。
以后在这台机子上做性能验收，只看 p50/p95 绝对值，不看 Janky%。

逐项关掉做减法（同一套「10 次回顶 + 4 次 700ms 慢拖」脚本）：

| 实验 | 改动 | p50 | p95 | GPU p50 |
| --- | --- | --- | --- | --- |
| — | 第一轮修完（玻璃开、mask 在） | 10~11 | 14~21 | 5 |
| E1 | 关玻璃底色录制 | 9 | 14 | 3 |
| E2 | 行封面改硬件圆角裁剪 | 8 | 13 | 3 |
| E3 | 只留 6 行（255→143 view） | 8 | 12 | — |
| E4 | 卡片封面也改硬件圆角 | 9 | 12 | 3 |
| E5 | 玻璃开但冻结重录 | 9 | 11 | 3 |
| E6 | 玻璃滚动中限频 120ms | 9 | 11~12 | 3 |
| E8 | 两条横向轨道清空 | 9 | 11 | 3 |
| **对照** | **系统设置页（com.android.settings）** | **10** | **12** | **5** |

**结论：p50 9ms 是这台设备的 HWUI 基线，跟行数/轨道/玻璃/mask 全都无关。**
系统设置页比我们的推荐页还慢（p50 10ms、GPU 5ms），我们已经低于平台基线。
所以再往上抠已经没有空间了，剩下的只能是行为层问题（见下）。

**本轮实打实的收益（都保留）：**
- 新增 `music/ui/widget/CoverImageView`：`outline.setRoundRect` + `clipToOutline`，
  替换 `ShapeableImageView` 的 path mask。SW Path Mask 从 **7.99MB / 23 条** 降到 **482KB / 2 条**，
  GPU 少 1~2ms。踩坑记录：必须 `setRoundRect`，用 `setPath` 就又回 path mask 了。
- `GlassSurfaceView` 采样间隔分档：滚动中 120ms、静止 60ms、CPU 退路 200ms。
  实测「每 50ms 重录一次整页」单次约 2ms，每三帧顶一个尖峰 —— 这才是玻璃真正的代价，
  不是 RenderEffect。冻结重录（E5）后玻璃开销归零，证明记录才是成本。
- `RecommendCacheStore.write` 的 JSON 序列化挪到 `Dispatchers.IO`：
  调用点正好是「推荐结果到达、用户开始滑」那一刻，主线程 1~3ms 会直接顶掉一帧。

**90Hz 面板的测量陷阱（记下来）：**
- `input swipe ... 130`（快速 fling）比 `... 700`（慢拖）测出来差 3~4ms，因为 fling 尾巴长、
  每帧暴露的新内容多。**报告数据时必须说明用手势类型**，否则前后对比不可信。
- `dumpsys gfxinfo` 的 `framestats` 在 API 37 上不输出，别指望逐帧 CSV。
- `debug.hwui.overdraw` 在这台机子上无效（设了 show/count 截图都没变化）。
- 对照组一定要真的在前台：`am start -a android.settings.SETTINGS` 会被拦，
  必须 `am start -n com.android.settings/.Settings`，并且先 `dumpsys window | grep mCurrentFocus` 确认。
  否则会拿到 `4950ms` 这个「零帧」哨兵值，白测。

### 第三轮（18:50-19:00）：用户定位「松手滑行那段」

这个信息很关键 —— 卡的是 fling 减速阶段，不是拖动阶段。顺着查到了两个周期性尖峰：

**1. 玻璃底色采样在滑行期间每 120ms 顶一次 2ms（主因）**
一次 capture = 整页子树重录进 RenderNode + 重跑 RenderEffect，单次约 2ms，全在 UI 线程。
滑行时本来就 9ms/帧，多 2ms 直接过不了 11.1ms 的 vsync。
A/B：滑行期间冻结采样 → **p50 9→6ms、p95 13~18→8ms**。

改法 `GlassSurfaceView.captureDelayMs()`：**滚动中完全不采**，等 `SCROLL_SETTLE_MS=220ms`
没有滚动事件了再补一次清晰的；长拖兜底 `LONG_SCROLL_CAPTURE_MS=1000ms` 采一次，
免得长拖时玻璃里是化石画面。代价是滑行中那层磨砂背景是静止的 —— 60dp 强模糊条，看不出来。

**2. 播放位置回调每 350ms 让迷你播放器整块失效**
`MiniPlayerView.bind` 原来无条件 `setText` ×2 + `setImageResource`，
而这三个控件都在 `GlassSurfaceView` 里 —— 面板一失效就要重排一遍玻璃的渐变和描边。
逐项比对后一次 tick 只剩进度线（2dp）重画。顺带 `SeekLine.progress` 也加了值不变就不 invalidate。

**教训：滑行卡顿要先分清「拖动」和「fling」两个阶段。**
我前面几轮全用慢拖测，p95 一直很好看（10~11ms），完全掩盖了 fling 的问题。
`input swipe y1 y2 150` 之后的惯性段才是 90Hz 上最容易露馅的地方。

**测量噪声提醒**：同一配置连测 5 次，p95 会在 10~16ms 之间跳。
偶发一次 150ms 的帧（logcat 里既没 Choreographer skip 也没 GC 日志，未定位）。
判读时看多次的中位数和 p50，不要拿单次跑的结果下结论。

### 四段耗时账（`debug.hwui.profile`，同一个 4 次慢拖测到底）

| 阶段 | 推荐页 | 系统设置页 |
| --- | --- | --- |
| Draw（记录视图树） | 2.5ms | 2.1ms |
| Prepare（动画/ripple） | 1.1ms | 0.37ms |
| Process（= Draw+Prepare 主体） | 3.6ms | 2.6ms |
| Execute（合成提交） | **2.3ms** | **4.9ms** |
| GPU | **3ms** | **5ms** |

**结论口径**：我们的 UI 线程比系统应用多约 1ms（255 个 view 的显示列表记录 + ripple 动画），
但合成提交和 GPU 各少 2~2.6ms，**总账打平甚至更好**。所以「还有某个功能在吃性能」这个方向
已经走完了 —— 剩下的是这台机器画一帧的固定成本。

**卡顿的真实机制（跟平均帧耗时不是一回事）**：
90Hz 预算 11.1ms，常态 9ms 只剩 2.1ms 余量。只要有任何**周期性**尖峰
（玻璃原来每 120ms 一次 2ms、迷你播放器每 350ms 一次整块失效），
那一帧就被顶到 13~18ms → 直接掉一整个 vsync。
所以「平均 9ms、jank 0.4%」和「肉眼一顿一顿」可以同时成立。
**排查顺序应该是：先找周期性，再看平均值。**

### 查证：别人家的玻璃为什么不卡（19:05）

结论写进 `MEMORY.md` 了（「玻璃 / 模糊效果的平台事实」）。三条要点：

1. **Android 没有同窗口 backdrop blur**。`RenderEffect` 只模糊 view 自身，
   想看穿背后就必须 `RenderNode` 录制 —— 我们走的正是这条路，没有更便宜的实现。
   跨窗口 `setBackgroundBlurRadius` 由合成器做、几乎免费，但只能用于独立窗口。
2. **iOS 的 UIVisualEffectView 是合成器级**，架构差异，不是写法差异。
3. **网易云/QQ 音乐的播放页背景是「封面图 + StackBlur」的一次性静态图**
   （搜到的仿网易云教程里就是这么做的），滚动时那张图根本不更新 ——
   所以它们不卡，因为做的不是实时模糊。

真做实时的开源方案（haze / expo-blur / RN Liquid Glass 复刻）共用的三招：
降采样捕获、内容哈希脏检查、按 GPU 分级砍效果。

**我们缺的两招**：① 录制前不降采样（现在是全分辨率 1216×2640 的 node）
② 录制范围是整页（400 个 view）而不是面板后面那一条。
`GlassBackdrop.kt` 类注释写的是「录一个面板大小的 node」，实际代码是 `beginRecording(source.width, source.height)`
**全屏尺寸** —— 注释和实现对不上，这也是它贵的原因之一。

### 落地：只录面板背后那一条（19:10）

`RenderNodeBackdrop.record` 加 `clipRect`：按面板在源坐标系里的矩形（`-dx, -dy` 起）裁剪，
ViewGroup 画子树时会按裁剪矩形剔除视野外的子 View，于是参与录制的只剩面板后面那几行。

**关键教训：只能 clip，不能 translate。** 之前注释里写的「canvas 先平移再画」实测录出空图 ——
平移后子 View 的边界判定全部落空。这条写进类注释了，别再试第二次。

收益：单次 capture 从约 2ms 降到可接受，于是**滚动中的采样可以恢复**（200ms 一次），
不必再靠「滑行中完全不采」来保帧率。观感上玻璃重新跟随内容，而不是冻结。

滑行 p95 序列（同机同脚本）：

| 配置 | p95 |
| --- | --- |
| 整页录制 + 50ms 采样（最初） | 17~21ms |
| 整页录制 + 120ms 采样 | 13~18ms |
| 整页录制 + 滑行不采样（玻璃冻结） | 8~11ms |
| **只录面板 + 200ms 采样（玻璃跟随）** | **9~15ms，中位 12** |

方差很大（同配置连测 4 次能差 6ms），判读只看中位数趋势。
结论：实时折射在这台机器上就落在 11.1ms 预算边缘，能跟手但不可能「稳过」。
要绝对流畅只有改成静态模糊图（网易云那条路）。

### 决策：删掉液态玻璃，只留高斯模糊（19:30）

用户拍板「不要玻璃效果了，只使用高斯模糊」。这不是改开关，是把那条路径整条删掉：

- `GlassMode` enum 删除，`GlassSpec` 只剩 `frost`（原来是 `mode + frost`）
- `RenderNodeBackdrop` 删掉 `RuntimeShader` 字段和整段 `REFRACTION_AGSL`，
  `effectFor(spec)` 只返回一个 `createBlurEffect`
- `GlassPainter` 删掉所有 `liquid` 分支：斜向反光、bevel、底部收口、边缘色散（fringe）、
  触摸镜面（lensPaint / RadialGradient）
- `GlassSurfaceView` 删掉 `lensFollowTouch` / `lensFade` / `dispatchTouchEvent` 重写 / `fadeLens`
- `GlassDialog` 删掉「液态玻璃 / 高斯模糊」二选一那行（`buildModeRow` / `pickMode` / `applyModeLook`），
  `dialog_glass.xml` 里对应的 `glassMode` 容器一起删
- `strings.xml` 删 `glass_mode_liquid` / `glass_mode_blur`

**磨砂下限改成 0.3**：旧 prefs 里存过 `frost = 0`（液态时代 0 还有折射撑着轮廓），
纯高斯下 0 就只是一层几乎不模糊的染色，看着像坏掉的透明卡片。

### 调研：Kyant0/AndroidLiquidGlass（Backdrop）怎么做到不卡的（19:50）

4.7k stars 的 Compose Multiplatform 液态玻璃库，2.0.1 已改名 **Backdrop**。
读了 `kmp` 分支的核心源码，性能靠四件事，没有一件是黑魔法：

**1. 背景只录一次，多个玻璃共享（最关键）**
`LayerBackdrop` 持有一个 `GraphicsLayer`，背景内容通过 `rememberLayerBackdrop()` 录进去一次。
玻璃采样时只是 `translate(-offset)` + `drawLayer(layer)` —— 一次纹理 blit。
我们是每个玻璃面板各录一遍整页（迷你播放器 + 导航栏 = 2 次全页录制）。
**这是最大的架构差距。**

**2. 玻璃自己的 layer 尺寸 = 面板尺寸 + padding，不是全屏**
`recordLayer(layer, size = IntSize(size.width + padding*2, ...))`。
Compose 的 layer 录制可以自由平移 canvas，不受 ViewGroup 裁剪约束 ——
我们当年在 View 体系里试"只录面板那条"，`View.draw()` 的子 View 剔除逻辑直接录出空图，
所以只能录全屏。**这条在 XML View 里做不到，除非换 Compose。**

**3. SDF 是解析式，不生成纹理**
`sdRoundedRect()` 就 4 行数学（`length(max(cornerCoord,0)) - radius`）。
对比中文社区那篇复刻 iOS 液态玻璃的博客："每帧生成 SDF，高端机只有 15~20fps" ——
他慢是因为每帧生成 SDF 贴图，Kyant 根本没生成。

**4. 折射只在边缘带算，中心早退**
```glsl
if (-sd >= refractionHeight) { return content.eval(coord); }  // 一次采样，直接返回
```
只有离边框 < `refractionHeight` 的像素才做折射偏移和额外采样。
我们当年那个 AGSL **每个像素都算** `t`、`dir`、`pow(t,2.2)*bend`，没有早退 ——
这是同样做折射却更贵的直接原因。色散（7 次 `content.eval`）是可选开关，默认不开。

另外两个小手段：`RuntimeShaderCache` 全局 `Map<key, RuntimeShader>`（AGSL 只编译一次）、
`observeReads` + `invalidateDrawCache()` 只在 effect 依赖变化时重建 renderEffect。

**Blur 的 padding 有个细节**：`if (edgeTreatment != Clamp || renderEffect != null) padding = max(padding, radius)` ——
`Clamp` 时模糊靠拉伸边缘像素，不需要额外 padding；只有需要采样边界外内容时才扩边。

**给以后的我**：真要恢复实时模糊，正确架构是「共享 backdrop layer + 面板局部采样」，
而不是「每个面板各录一遍整页」。前者在 Compose 里天然可行，在 XML View 里做不到。

## 修复：推荐页下半部分曲目"不飞入"（透明卡死）

**现象**：冷启动打开 App，上半部分（标题/每日卡）正常飞入，下半部分曲目列表不动 ——
截图中前 6 行位置空白，只有第 7、8 行能看到。

**根因**：`RecommendFragment.animateRows` 对 RecyclerView 的前 6 个 **child** 逐个
`springEnter`，而 `springEnter` 是「先写 `alpha=0 + translationY`，再靠带 startDelay 的
ValueAnimator 推回终态」。child 是 ViewHolder.itemView，会被后续 submitList
（收藏、静默同步都会触发 renderTracks → submitList）重新绑定/拆装；动画中途被打断后
`alpha=0` 永久留下。第 7 行往后超出 `ROW_ENTRANCE_MAX=6` 没被碰，所以正常显示 —— 这正是
"只有上半部分飞入"的真相，不是没播动画，是前 6 行被写透明后卡住了。

**修复（2 处文件）**：
1. `Spring.kt` `springEnter`：加 `postDelayed(delay + duration + 200ms)` 归位兜底 ——
   超时后若 view 仍 `alpha<0.99` 或位移未归零，并且没有被新动画接管（`runningAnimators[this] === animator`），
   强制落终态。所有用 springEnter 的地方都受益。
2. `RecommendFragment.kt`：曲目列表改成**整个 RecyclerView 作为稳定 View 一次 springEnter**，
   child 怎么复用都不影响；删掉 `userScrolled` 早退守卫（它会在数据晚到且用户滑过时让整列"啪"地出现）、
   `ROW_ENTRANCE_MAX`/`ROW_STAGGER_MS` 常量和 scroll 监听。`rowsEntered` 只守卫这一个整体动画。

**验证**：`assembleDebug -PapiBaseUrl=http://127.0.0.1:8080/` BUILD SUCCESSFUL。
真机装包被设备端权限弹窗拒绝（INSTALL_FAILED_ABORTED: User rejected permissions），未录屏抽帧。

**经验（可推广）**：绝不要对 RecyclerView child 直接做「先写透明初始态 + 延迟动画归位」的入场 ——
child 的生命周期归 RV 管，动画和复用必然打架。要么动画整个容器，要么在 Adapter.onBind 里
用 payload/标志位驱动一次性动画。

## 诊断：音源管理登录了仍拿不到 VIP 歌（20:32，只诊断未改码）

## 导航外框曲率对齐胶囊（21:00 修复）

- 用户反馈：导航栏外框圆角和选中胶囊高光的曲率不一致。
- 根因：外框（面板染色/描边/轮廓）走 `Squircle.path` 默认 exponent 4.2（连续曲率、偏方），
  而选中胶囊 `drawPill()` 用 `addRoundRect(半径=半高)`，是纯圆弧（等价 exponent 2）。
- 修法：`GlassPainter` 加 `cornerExponent` 字段（默认 4.2），`configure` 带该参数，
  `buildPaths` 三条路径都传它；`GlassSurfaceView` 加 `cornerExponent` 属性（setter 触发重绘+重算 outline），
  `syncGlass` 和 outlineProvider 都跟着传；`BottomNavBar` 设 `cornerExponent = 2f`，
  自己的 `barPath`（onSizeChanged 里）也传它。迷你播放器仍是默认 4.2，不受影响。
- 验证：编译装机截图放大，外框已变纯圆弧、和胶囊曲率一致。截图已清。

## 校园网无线联调可行性 + 在线音源能力边界（21:03 答疑，只读未改码）

用户问「电脑开后端、手机不插线用 App，校园网怎么办」「能否自己连音源播歌」。

  `198.18.0.1`（Mihomo TUN）、`10.202.52.23`（WLAN 校园网）、`192.168.137.1`
  （Microsoft Wi-Fi Direct Virtual Adapter #2，Windows 移动热点网关）。
  推荐开电脑移动热点，App 填 `http://192.168.137.1:8080/`；Mihomo TUN 可能劫持热点段，需 DIRECT 或关。
- **修正 MEMORY.md 的过时结论**：旧记录写「酷我客户端直连，后端挂了仍能搜能播」，实际代码里
  酷我 anti.s 接口失效（返回「请下载酷我 App」提示音）已全链路停用。
  `OnlineSourceRouter.search()` 后端离线直接返回空 + OFFLINE_HINT_NO_SOURCE；
  网易云/酷狗/QQ 只有后端实现 → **后端不可达 = 在线音源完全不可用**，是刻意诚实降级。
- 离线可播的只有本机曲库（MediaStore）+ 收藏 + 上次推荐缓存：`LocalRecommendEngine` 只从
  本机曲库/收藏出歌，`fallbackFeed()` 同理；`PlayableFilter` 对非 ONLINE 且 uri 非空的曲目直接放行，
  本地曲目能进播放队列。
- 结论口径：想在线听歌必须后端可达（热点方案或内网穿透）；只演示主流程，手机预置本地 mp3 即可离线播。
